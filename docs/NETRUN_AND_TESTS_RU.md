# Nexcent: Netrun, Adminer и тестирование

Практическая инструкция к лабораторной работе №4. Версия проекта 5.2. Дата подготовки: 12.11.2026.

## 1. Что подготовлено

В корне архива находится весь проект: сайт, Express API, SQL-схема, конфигурации запуска и тесты. Загружайте архив целиком; в его корне должны быть compose.yaml и package.json. Рабочие пароли, node_modules и дампы базы в архив не включены.

Основная конфигурация compose.yaml предназначена для Netrun: web (Nginx) принимает HTTP на 8080, app выполняет Node.js, db хранит MySQL 8.4, adminer показывает таблицы. Платформа обеспечивает внешний HTTPS. MySQL не публикует порт в Интернет. Данные лежат в именованном томе mysql_data.

Старая VPS-конфигурация сохранена как compose.vps.yaml. Для этой инструкции она не используется. compose.test.yaml запускает только отдельную временную тестовую MySQL на localhost:3307. Не путайте эти файлы.

В приложении выделен server/domain.js: сумма заказа в копейках, проверка даты бронирования по Москве и допустимые переходы статусов. API использует эти же функции. Бизнес-правила и дизайн сайта сохранены.

Сайт пока не опубликован в вашем аккаунте Netrun. Локальный прогон не доказывает работоспособность HTTPS, тарифа и контейнеров на хостинге. Фактические результаты и ограничения приведены в qa/RESULTS_RU.md.

## 2. Что установить на Windows

1. Node.js 24 LTS с npm: https://nodejs.org/en/download. Откройте новый PowerShell после установки.
2. Docker Desktop: https://docs.docker.com/desktop/setup/install/windows-install/. Проверьте поддерживаемую версию Windows и требования WSL 2 на странице установки. Запустите Docker Desktop и дождитесь готовности.
3. Для ручной проверки используйте Chrome и Firefox. Автоматизированным тестам Playwright нужны собственные браузеры, которые устанавливаются командой ниже.

Откройте распакованную папку проекта в Проводнике. В адресной строке введите powershell. Все последующие команды выполняйте в этой папке, где лежит package.json.

```powershell
node --version
npm --version
docker compose version
npm ci
npx playwright install chromium firefox
```

Ожидается Node 24 или новее; npm ci устанавливает версии из package-lock.json. Если PowerShell запрещает npm.ps1, используйте npm.cmd вместо npm и npx.cmd вместо npx. Менять глобальную политику выполнения для этого не нужно.

## 3. Секреты для Netrun

Откройте https://netrun.io/, войдите и создайте проект загрузкой ZIP. Выбирайте развёртывание по существующему Docker Compose, если платформа запрашивает способ запуска. Содержимое .env.netrun.example служит списком настроек: реальные значения введите во вкладке «Секреты» проекта.

Если выбор публичного сервиса/порта доступен, укажите web и 8080. app:3000, db:3306 и adminer:8080 должны оставаться внутренними сервисами. Точные подписи элементов интерфейса могут отличаться.

| Переменная | Значение и назначение |
| --- | --- |
| NODE_ENV | production |
| APP_ORIGIN | Полный адрес сайта с https://, без завершающего / |
| DB_NAME | nexcent |
| DB_USER | nexcent |
| DB_PASSWORD | Случайный пароль пользователя MySQL, минимум 16 символов |
| MYSQL_ROOT_PASSWORD | Другой случайный пароль администратора MySQL |
| ADMINER_GATE_USER | dbviewer: имя для первого окна входа в Adminer |
| ADMINER_GATE_PASSWORD | Ещё один случайный пароль, минимум 16 символов |
| ADMIN_EMAIL | Ваш email для первого администратора сайта |
| ADMIN_PASSWORD | Отдельный пароль администратора сайта: от 8 символов, до 72 байт UTF-8 |
| ADMIN_NAME | Имя администратора сайта |
| ADMIN_PHONE | Телефон с кодом страны, например +79990000001 для учебного стенда |
| SEED_DEMO_REVIEWS | false: не добавлять демонстрационные отзывы при первом запуске |

LEGAL_OPERATOR_NAME, LEGAL_OPERATOR_ADDRESS и LEGAL_CONTACT_EMAIL нужны для подстановки реквизитов в политику. Если все три не заданы, остаётся предупреждение об учебном характере проекта. Не придумывайте реквизиты реальной организации.

Для генерации одного случайного пароля выполните локально следующую команду. Повторите отдельно для каждого секрета. Не вставляйте пароли в отчёт или переписку.

```powershell
node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"
```

Если публичный URL появляется только после первой сборки, временно задайте APP_ORIGIN=https://example.invalid. Как только Netrun выдаст адрес, замените значение на фактический HTTPS-адрес и перезапустите/переразверните проект. До этого формы не следует проверять: защита от запросов с другого origin отклонит отправку.

## 4. Первый запуск и обновление

После заполнения секретов запустите развёртывание. В логах db дождитесь готовности MySQL. app автоматически применяет схему, заполняет каталог и при совершенно пустой таблице users создаёт первого администратора из ADMIN_*.

Создание администратора не повышает права существующего аккаунта и не меняет прежние пароли. После успешного входа удалите ADMIN_PASSWORD из секретов; при последующих запусках bootstrap будет пропущен. ADMIN_EMAIL и ADMIN_PHONE могут остаться. Если users уже содержит записи, bootstrap ничего не создаёт: используйте существующий доступ или команду admin:create в консоли контейнера, если такая консоль доступна на хостинге.

Проверьте по выданному адресу:

```text
https://ВАШ-АДРЕС/api/health
https://ВАШ-АДРЕС/
https://ВАШ-АДРЕС/about.html#login
https://ВАШ-АДРЕС/admin.html
https://ВАШ-АДРЕС/adminer/
```

/api/health должен вернуть {"ok":true}. Войдите на сайт с ADMIN_EMAIL и ADMIN_PASSWORD, затем откройте /admin.html. Это интерфейс управления рестораном: блюда, пользователи, заказы, брони и отзывы.

В архиве есть схема и начальный каталог, но нет дампа вашей прежней рабочей БД. Поэтому новая БД сама по себе не содержит старых регистраций и заказов. Для переноса данных сначала получите SQL-экспорт старой базы; не импортируйте непроверенный дамп поверх новой рабочей базы без резервной копии.

Для обновления загружайте новую версию в тот же проект. Не удаляйте проект и том mysql_data. Не меняйте имя тома. После первого создания БД простая смена DB_PASSWORD или MYSQL_ROOT_PASSWORD в секретах НЕ меняет пароль внутри MySQL: пароль нужно менять согласованно в БД и настройках.

На Netrun для Compose сохраняются именованные тома; универсальный совет «положить всё в /data» здесь не применяется. Бесплатный сайт может засыпать, а ресурсы одного проекта делятся между четырьмя сервисами. Если MySQL завершается из-за нехватки памяти, смотрите логи и лимиты выбранного тарифа.

## 5. Как посмотреть базу, как на скриншоте

Откройте /adminer/. Сначала браузер спросит дополнительный логин и пароль: ADMINER_GATE_USER и ADMINER_GATE_PASSWORD. После этого появится форма Adminer.

| Поле Adminer | Что вводить |
| --- | --- |
| Система | MySQL |
| Сервер | db |
| Пользователь | nexcent, либо ваше значение DB_USER |
| Пароль | Значение DB_PASSWORD |
| База данных | nexcent, либо ваше значение DB_NAME |

Внутри Compose имя db означает контейнер базы. localhost в форме Adminer означал бы сам контейнер Adminer, поэтому здесь он неверен. Пароль от аккаунта сайта для этого входа не подходит.

Слева выберите users, затем «Выбрать»: увидите пользователей, как у друга. Аналогично доступны products, categories, cart_items, orders, order_items, bookings, feedback, user_sessions и user_actions. «Показать структуру» показывает поля, типы, ключи и индексы. «SQL-запрос» позволяет запускать SQL. «Экспорт» позволяет сохранить структуру и данные в SQL.

Для скриншота используйте тестовые записи. Не включайте в кадр пароли, токены сессий или чужие личные сведения. Для демонстрации пользователей достаточно безопасной выборки:

```sql
SELECT id, name, email, role, blocked, created_at
FROM users ORDER BY id DESC LIMIT 20;
```

Пароль пользователя хранится в password_hash, а не в password. Проверить формат, не выводя сам хеш, можно так:

```sql
SELECT id, LEFT(password_hash, 4) AS hash_prefix,
       LENGTH(password_hash) AS hash_length
FROM users LIMIT 5;
```

Для bcrypt ожидается префикс вроде $2b$ и длина 60. Сырой пароль из хеша восстановить нельзя. Полный пользователь БД nexcent может редактировать таблицы; для обычного просмотра используйте только SELECT и не нажимайте «Удалить».

## 6. Отдельная база для тестов

Тесты регистрации, заказов и админки создают/изменяют записи. Они должны выполняться на nexcent_test. Конфигурация содержит защиту по суффиксу _test и запрещает NODE_ENV=production, но вы всё равно должны использовать отдельные реквизиты.

```powershell
Copy-Item .env.test.example .env.test
docker compose -p nexcent-qa -f compose.test.yaml up -d --wait
npm run test:init
```

Тестовая MySQL доступна на 127.0.0.1:3307. Содержимое .env.test.example уже соответствует compose.test.yaml. Тестовый пароль в примере не является рабочим секретом и предназначен только для локального стенда.

Если порт 3307 занят, поменяйте левую часть привязки в compose.test.yaml и DB_PORT в .env.test. Сервер приложения будет на http://localhost:3000.

Данные тестовой БД лежат во временном tmpfs. Для полного сброса только тестового стенда выполните:

```powershell
docker compose -p nexcent-qa -f compose.test.yaml down
docker compose -p nexcent-qa -f compose.test.yaml up -d --wait
npm run test:init
```

Не заменяйте -f compose.test.yaml на основной compose.yaml в командах сброса. Для повторных браузерных сценариев чистая тестовая база удобнее: накопившиеся брони могут занять доступную вместимость.

## 7. Какие тесты запускать и что они проверяют

| Команда | Проверки |
| --- | --- |
| npm run test:unit | 78 изолированных проверок валидации, расчётов, переходов статусов, экранирования и проверок доступа |
| npm run coverage | Те же unit-тесты плюс покрытие validation.js и domain.js; порог 60% для строк, функций и ветвей |
| npm run test:integration | 41 проверка API, регрессий, ограничений БД и безопасности; нужна nexcent_test |
| npm run test:db | Только 10 проверок БД из общего набора |
| npm test | Сначала unit, затем интеграционный набор |
| npm run test:e2e | 14 сценариев качества интерфейса: 7 в Chromium и 7 в Firefox |
| npm run test:browser | Полный пользовательский сценарий в Chromium |
| npm run test:browser:firefox | Полный пользовательский сценарий в Firefox |
| npm run test:smoke | Проверки опубликованного адреса; нужен BASE_URL |
| npm run test:load | Два локальных прогона: 100 запросов при параллельности 10 и 50 |

Пример порядка запуска и сохранения вывода в PowerShell:

```powershell
New-Item -ItemType Directory -Force test-results
npm run coverage 2>&1 | Tee-Object test-results/coverage.txt
npm run test:integration 2>&1 | Tee-Object test-results/integration.txt
npm run start:test
```

Последняя команда запускает сервер и занимает терминал. Оставьте его открытым. Во втором PowerShell, из той же папки, выполните:

```powershell
npm run test:e2e
npm run test:browser
npm run test:browser:firefox
npx playwright show-report
```

Playwright создаёт playwright-report/index.html, а снимки и трассировки помещает в test-results. Полный сценарий делает регистрацию, перенос гостевой корзины, заказ, отзыв, бронь, поиск, просмотр кабинета и редактирование администратором. Назначение роли происходит SQL-запросом только в тестовой базе.

Unit-тест не требует сервера и БД: например, функция orderTotal получает цены 0.10 и 0.20 и проверяется точный итог 0.50. Интеграционный тест отправляет запрос в Express и проверяет реальные строки в БД. Браузерный тест нажимает кнопки, вводит данные и проверяет отображение. Эти уровни дополняют друг друга.

Чтобы написать ещё один тест, выберите правило, задайте вход, выполните действие и сравните результат с ожидаемым. Добавляйте негативный случай и границу диапазона. Не подменяйте ожидаемый результат тем, что случайно вернуло приложение.

```javascript
import test from 'node:test';
import assert from 'node:assert/strict';
import { orderTotal } from '../../server/domain.js';

test('два блюда по 690 рублей', () => {
  assert.equal(orderTotal([{price:690, quantity:2}]), 1380);
});
```

Такой файл можно положить в test/unit/extra.test.js; npm run test:unit подхватит его автоматически. Для интеграционных тестов используется supertest и отдельная база. Смотрите test/api.test.js и test/database.test.js как рабочие образцы.

## 8. Проверки БД и безопасности для отчёта

В test/sql/audit.sql находятся 10 запросов только для чтения: дубликаты email/телефонов, пустые обязательные поля, потерянные связи и несовпадение суммы заказа с его позициями. Каждый запрос должен вернуть 0 строк. Запустите их в Adminer и сохраните скриншоты.

Автоматические тесты дополнительно проверяют NOT NULL, UNIQUE, внешние ключи, CHECK, каскадное удаление и откат транзакции после ошибки. Проверка checksum сопоставляет применённую миграцию с sql/001-schema.sql. Старую применённую миграцию нельзя редактировать произвольно: это вызовет отказ запуска, защищающий схему от незаметного расхождения.

ER-диаграмму можно получить в DBeaver на локальной тестовой базе: MySQL, 127.0.0.1, порт 3307, база/пользователь nexcent_test, пароль из .env.test. Откройте список таблиц, выделите их и выберите ER Diagram. Производственный MySQL специально не доступен по внешнему порту; не открывайте 3306 ради скриншота.

Автотесты проверяют CSRF, origin, запрет повышения роли через профиль, доступ к чужим заказам, отзывам и избранному, SQL-инъекции в поиске/входе, хеши паролей, смену/завершение сессий, ограничение попыток входа, CSP и недоступность исходников. Это набор проверок, а не доказательство отсутствия всех уязвимостей.

После публикации задайте адрес в отдельном PowerShell:

```powershell
$env:BASE_URL = "https://ВАШ-АДРЕС"
npm run test:smoke
Remove-Item Env:BASE_URL
```

Smoke проверяет страницы, API/БД, заголовки, атрибуты cookie, HTTPS-перенаправление, закрытый Adminer и недоступность служебных файлов. Его результат сохраняется в test-results/smoke.json. Не запускайте test:browser против рабочей базы: там создаются записи и назначается роль.

Дополнительно по методичке выполните securityheaders.com и SSL Labs для собственного публичного домена, сохраните их фактические оценки. Оценки заранее не гарантируются. Для OWASP ZAP сначала выполните пассивный анализ трафика; активный скан применяйте к своему отдельному тестовому стенду с синтетическими данными. Запишите High/Medium/Low/Informational, исключения и ложные срабатывания. Сканирование и рейтинги не выполнены при подготовке архива.

Для ручной XSS-проверки на тестовом стенде введите <script>alert('XSS')</script> в отзыв, опубликуйте его через админку и убедитесь, что текст показан буквально, а окно alert не появляется. Проверьте также имя пользователя и ответ администратора. Для SQLi можно использовать строку ' OR 1=1 -- в поиске и входе: не должно быть обхода авторизации, SQL-ошибок или выдачи всех строк.

## 9. UX, доступность и производительность

Автоматический тест адаптивности проверяет страницы на 360, 768 и 1440 px, отсутствие горизонтального переполнения, загрузку изображений и локальных ресурсов, ошибки JavaScript. Отдельные сценарии проверяют минимум 10 внутренних назначений ссылок, HTML-валидацию email, мобильное меню с клавиатуры, alt и подписи полей. Это не полноценное исследование удобства с реальными пользователями.

В Chrome нажмите F12 и проверьте Network после перезагрузки: локальные CSS/JS/изображения не должны отдавать 404/500. При HTTPS не должно быть загрузки HTTP-ресурсов. В Console не должно быть ошибок. В Device Toolbar задайте три требуемые ширины и сохраните снимки. В Firefox повторите основные действия.

Запустите Lighthouse в Chrome DevTools: Navigation, категории Performance, Accessibility, Best Practices, SEO. Сохраните HTML-отчёт и снимок оценок. Цели методички: Accessibility не ниже 90, Performance не ниже 80. Это целевые значения, а не результаты текущей проверки.

В Performance запишите загрузку главной страницы. В отчёте отдельно укажите первый запрос после сна и повторную «тёплую» загрузку; ориентир задания - до 3 секунд. Для WAVE используйте https://wave.webaim.org/ и зафиксируйте контраст, заголовки и подписи. Если ресурс не может открыть стенд, используйте расширение в браузере.

Пройдите сайт клавишами Tab, Shift+Tab, Enter и Esc. Проверьте видимость фокуса, порядок перехода, открытие/закрытие диалога блюда, доступность корзины и форм. Вручную проверьте размеры основных кнопок не менее 44x44 px. Запишите 3-5 наблюдений: что удобно, что мешает и как это исправить, исходя из реального прогона.

## 10. Нагрузочное тестирование

При запущенном локальном тестовом сервере:

```powershell
npm run test:load
```

Скрипт выполняет один прогрев, затем ровно 100 GET-запросов главной страницы с 10 параллельными запросами. После этого повторяет прогрев и 100 запросов с параллельностью 50. Ответы вычитываются полностью. Ошибки сети и статусы, отличные от 200, учитываются отдельно. Записи в БД не создаются.

В test-results/load.json сохраняются success, errors, rps, mean_ms, p95_ms и max_ms. p95 означает время, быстрее которого завершились 95 из 100 запросов. Сравните среднее и p95 между двумя уровнями; большой рост задержек указывает на ограничение ресурса, но сам по себе ещё не доказывает, что виновата именно БД.

Для своего сайта на Netrun, после проверки лимитов и правил платформы:

```powershell
$env:BASE_URL = "https://ВАШ-АДРЕС"
$env:ALLOW_REMOTE_LOAD = "YES"
npm run test:load
Remove-Item Env:ALLOW_REMOTE_LOAD
Remove-Item Env:BASE_URL
```

Дополнительный сценарий k6 лежит в test/load.k6.js: 30 секунд роста до 10 пользователей, минута до 50, 30 секунд снижения. Он создаёт существенно больше 200 запросов. Устанавливайте k6 по https://grafana.com/docs/k6/latest/set-up/install-k6/ и запускайте на своём стенде отдельно:

```powershell
k6 run -e BASE_URL=http://localhost:3000 test/load.k6.js
```

Пороги k6: p95 < 500 мс, доля HTTP-ошибок < 1%. Это критерии сценария, не обещание производительности бесплатного тарифа. Сохраняйте реальный результат, даже если пороги не выполнены.

## 11. Что приложить к отчёту

1. Обоснование PaaS/Compose: Node.js и MySQL нужны одновременно; постоянный том сохраняет данные; Netrun предоставляет HTTPS и поддомен.
2. Скриншот состава проекта, секретов с ЗАКРЫТЫМИ значениями, успешной сборки и публичного сайта.
3. Скриншот /api/health, входа в админку сайта и Adminer с тестовыми таблицами.
4. Функциональный чек-лист с фактическими PASS/FAIL, комментарием, браузером и датой. Шаблон - docs/CHECKLIST_RU.md.
5. Вывод unit/integration, отчёт покрытия с указанием именно двух ключевых модулей; не называйте его покрытием всего проекта.
6. ER-диаграмма, результаты audit.sql, доказательство отката и неизменности данных после повторного init.
7. Результаты HTTPS, securityheaders, SSL Labs, ZAP и ручных XSS/SQLi-проверок.
8. Три ширины экрана, две версии браузеров, Lighthouse/WAVE и выводы по UX.
9. Таблица нагрузки: 100/10 и 100/50, RPS, среднее, p95, успешные ответы и ошибки. Локальные результаты и Netrun оформляйте раздельно.
10. Вывод: что прошло, какие дефекты исправлены и что остаётся ограничением среды/тарифа.

## 12. Частые ошибки

| Симптом | Что проверить |
| --- | --- |
| 502/503 | Логи web/app/db, готовность базы, выбран ли web:8080, хватает ли памяти |
| Access denied for user | DB_USER/DB_PASSWORD; смена секрета не меняет старый пароль в томе |
| ECONNREFUSED | Готовность MySQL; внутри Compose DB_HOST=db, локально для тестов 127.0.0.1:3307 |
| Формы возвращают 403 | APP_ORIGIN должен точно совпадать с адресом вкладки; обновите страницу после перезапуска |
| После входа снова гость | HTTPS, Secure-cookie и адрес APP_ORIGIN; localhost-тесты используют development |
| 429 у всех посетителей | Проверьте, какие X-Forwarded-For передаёт входной прокси Netrun; не отключайте rate limit вслепую |
| Adminer показывает 401 | Сначала введите ADMINER_GATE_USER/PASSWORD, затем отдельные реквизиты MySQL |
| Администратор не создаётся | ADMIN_* заданы полностью при первом запуске; users должна быть пустой |
| Ошибка checksum миграции | Верните исходную применённую схему; дальнейшие изменения оформляйте новыми миграциями |
| Playwright не запускает браузер | Выполните npx playwright install chromium firefox; на Linux могут понадобиться системные зависимости |
| E2E не соединяется с сайтом | В первом терминале должен работать npm run start:test, BASE_URL не должен указывать на старый хостинг |
